# Software Testing Homework Instructions

These instructions apply to every assignment and every file under this directory.

## Authoritative Sources and Precedence

- The course-wide rules extracted from `___2026.Homework.Policies.pdf` are embedded in this file and are the default working rules.
- Do not reopen or reread `___2026.Homework.Policies.pdf` for routine tasks. Consult it only when the student explicitly requests verification against the original, when a rule in this file is ambiguous, or when there is evidence that the PDF has changed.
- When starting a new assignment, read its assignment-specific PDF and materials once before producing or changing work. Reuse the extracted requirements during the same assignment instead of rereading unchanged files for every task.
- Extract and track all requirements, deliverables, grading criteria, file-format rules, and submission constraints.
- Follow, in descending priority: the lecturer's latest explicit instructions, the current assignment specification, the AI Usage Guideline, this file, and general conventions.
- If instructions conflict, are ambiguous, or require information that is not available, stop and ask the student instead of guessing.

## Individual Work and AI Use

- Treat every assignment as individual work unless the lecturer explicitly states otherwise.
- AI may assist, but the student must understand, review, and take responsibility for all submitted work.
- Make AI usage transparent and help the student prepare the disclosure required by the AI Usage Guideline and the lecturer.
- Never fabricate test execution, test results, defects, screenshots, measurements, citations, peer reviews, Git history, or other evidence.
- Clearly label anything that has not been executed or independently verified.

## Testing Quality

- Apply the correct software-testing techniques methodically, not merely superficially.
- Optimize for meaningful coverage, well-designed test cases, and valid defects. The number of test cases and discovered bugs may affect grade differentiation, but quantity must not replace correctness.
- Preserve reproducible evidence for test execution and discovered defects.
- For each defect, distinguish expected behavior, actual behavior, reproduction steps, environment, severity or impact, and supporting evidence when applicable.
- Complete the assignment's self-assessment rubric honestly and support the proposed grade with evidence.

## Required File Formats

- Use text-based source files for assignment submissions.
- Prefer Markdown. LaTeX is also acceptable when appropriate.
- Do not submit Word as the primary working format; convert Word-based work to Markdown.
- Excel may be used when needed, but copy its resulting summary tables into the Markdown report.
- For presentations, prefer Markdown presentation mode where practical.
- Produce a Save-As-PDF version of every submitted Markdown or LaTeX document.
- Keep required content inside the submission files. Do not rely excessively on online links; misuse or over-reliance on online links can result in a score of zero.

## Git and Work History

- Use Git to manage the version history of assignment files. GitHub, Bitbucket, and GitLab are acceptable repository hosts.
- Break every requirement into meaningful steps and create a clear, explicit commit for each completed step.
- Commit messages must describe what was done and which requirement or step it addresses.
- Do not create fake, retroactive, misleading, or bulk-only history intended to imitate incremental work.
- Preserve Git logs so they can be submitted when required.

## Project Collaboration and Peer Review

- For project-related assignments, ensure the student's assigned work does not overlap with another team member's work.
- Consider both task significance and difficulty. Warn the student when a chosen task may be too simple to qualify for a high grade.
- Peer reviews must identify concrete, constructive improvements. Praise-only reviews are insufficient.
- Do not write a review claiming that another person's work was inspected unless the relevant work was actually provided and reviewed.

## Submission Requirements

- Submission is through Moodle.
- Late submissions are not accepted except for important reasons such as critical health or family emergencies. Such exceptions require timely email notification to the instructors and full supporting evidence.
- The submission may contain at most 20 files, and each file must be no larger than 20 MB.
- If necessary, prepare split ZIP archives while preserving clear names and contents.
- The final submission archive must follow this exact naming format:

  `StudentID_ExerciseID_SelfAssessedGrade.zip`

- `SelfAssessedGrade` must be exactly three digits from `000` through `100`, including leading zeros when needed.
- Strictly comply with all submission rules. A violation may result in a score of zero.
- Treat every violation of the course Anti-Cheat regulations as academic dishonesty and do not assist with concealing or misrepresenting authorship.

## Mandatory Completion Check

Before declaring an assignment ready, verify and report:

1. Every requirement in the current assignment specification is addressed.
2. The required testing techniques were applied correctly.
3. All claimed executions and results have real supporting evidence.
4. The self-assessment rubric is complete and the proposed grade is justified.
5. The Markdown or LaTeX source files and corresponding PDF copies are present.
6. Excel summary tables, if any, are also included in the Markdown report.
7. The archive name exactly matches `StudentID_ExerciseID_SelfAssessedGrade.zip`.
8. The self-assessed grade is a three-digit value from `000` to `100`.
9. There are no more than 20 submitted files and no file exceeds 20 MB.
10. Required content is included directly rather than depending on online links.
11. Git history contains clear commits for meaningful requirement steps.
12. AI usage is disclosed as required.
13. Any remaining limitations, assumptions, or unverified claims are explicitly listed.

## Final Response Format

When helping with an assignment, end with a concise status covering:

- requirements completed;
- tests and checks actually performed;
- defects or findings supported by evidence;
- remaining limitations or unverified claims;
- required submission files and naming;
- Git status and the recommended next commit;
- final policy-compliance checklist.
